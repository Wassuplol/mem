# 02 — OSS Discord-Bot Landscape & Red-DiscordBot Deep Dive

*Research date: 2026-10-07. Method: GitHub REST API (repo metadata, releases, release history), live fetches of repos/docs/releases, PyPI/npm registries, Red-Index machine data (`index/1-min.json`), and community sources. All star counts, dates and versions are as measured on 2026-10-07 unless stated.*

---

## 1. Red-DiscordBot today (Oct 2026)

**Repo state.** `Cog-Creators/Red-DiscordBot` — 5,724 stars, 2,521 forks, ~200 open issues + ~99 open PRs, GPL-3.0, Python. Last commit on the development branch `V3/develop`: **Sep 7, 2026** (a docs commit); before that Jun 21, Jun 17 (×2), May 30, May 28, May 17, 2026 — roughly 1–3 commits/month, overwhelmingly maintenance (OS support churn: "Support Fedora 44, drop Fedora 42 and RHEL 9.4 derivatives", install-guide fixes, Java version corrections). The only user-visible feature in that window was [Streams] kick.com support (#6547, May 17, 2026).

**Releases.** Latest stable: **3.5.24 (2026-03-06)**, preceded by 3.5.23 (2026-03-04), 3.5.22 (2025-09-04), 3.5.21 (2025-08-26), 3.5.20 (2025-05-03), 3.5.19, 3.5.18, 3.5.17, 3.5.16, 3.5.15 (Feb 2025), 3.5.14 (Dec 2024). So: bursts of maintenance releases, with **~6-month gaps (Sep 2025 → Mar 2026) and now 7 months with no stable release (Mar → Oct 2026)**. Development continues on a `3.5.25.dev` line. The project's own milestone page shows the next breaking release ("Breaking release after the next", i.e. 3.6.0) at **1/51 issues closed, no due date**; the changelog announces only that armv7l support will be dropped "in Red 3.6.0". Realistically: Red is maintained by a handful of volunteers (release credits list 5–13 people) at a slow, mostly reactive cadence.

**Python support — the big structural problem.** PyPI metadata for Red 3.5.24: `requires_python: >=3.8.1, <3.12`. The Ubuntu 24.04 install guide tells users to install **Python 3.11 via the deadsnakes PPA**. In a world where Python 3.14 is current (Oct 2026) and libraries are dropping <3.12, Red cannot run on any Python released since Oct 2023. This is the single clearest example of accumulated platform debt in the OSS ecosystem.

**Security history.** Two GitHub security advisories are published: "Incorrect Authorization in commands API" (GHSA-5jq8-q6rj-9gq4, Jul 10, 2024, Moderate) and "Unauthorized privilege escalation in Mod module" (GHSA-mp9m-g7qj-6vqr, Oct 27, 2020, Moderate), plus a historical RCE in the Trivia module fixed in 3.3.11 (GHSA-55j9-849x-26h4). These are core-cog bugs, fine — but they illustrate that Red's model of running *third-party code with full bot privileges* means every bug is a potential bot-takeover, and the mitigations are process-based only (below).

**Praise / why people stay.** Reddit and self-hosting communities consistently cite the same virtues: fully open source, self-hosted (your data, no paywalled tiers — a recurring complaint against MEE6/Dyno is "they all have paywalls… hide features behind paywalls"), and extreme extensibility via cogs ("open source, self-hosted and extensible with Python scripts (called cogs)"). The ecosystem is real: the Red-Index (fetched today) lists **105 repos containing 1,306 cogs**, of which **605 (46%) were updated in the last 12 months** — healthy for a 7-year-old platform. Red's docs (`docs.discord.red`) are excellent: per-release "Read before updating" sections, an explicit versioning/guarantees page, install guides for ~20 OSes.

**Complaints / why people leave.** (a) No dashboard — see §1.2; the official-org dashboard was *archived as "completely non-functional"*. (b) Prefix-command-centric UX with community anxiety about Discord's API shifts (Discussion #5842: "When slash commands are forced will this bot be impossible to use?"). (c) Setup/maintenance burden: virtualenvs, a Python version ceiling, and an Audio stack that depends on a **Java runtime + manually updated Lavalink jars** (3.5.23 moved to Java 17+, 3.5.24 added Java 21). The open-issue list is dominated by audio breakage. (d) Slow releases and a "we will not support the development version" policy — users who want fixes must run unsupported code. (e) Hosted alternatives (MEE6, Dyno, Carl-bot, Wick) win on out-of-the-box UX; Red wins on freedom, and the migration narrative is usually "I outgrew the paywall", not "Red is easier".

### 1.1 How the cog/plugin system actually works

- **Unit of distribution:** a "cog" = a Python package folder (`__init__.py` exposing `async def setup(bot)`, plus `info.json`). Repos are plain git repos (GitHub/GitLab), with a repo-level and per-cog `info.json` describing `requirements`, `min_bot_version`, `max_bot_version`, `min_python_version`, `end_user_data_statement`, `tags`, `type` (`COG` or `SHARED_LIBRARY`; shared libraries deprecated since 3.2).
- **Install/update flow (Downloader cog):** `[p]repo add <name> <url> [branch]` → `[p]cog install <repo> <cog>` → `[p]load <cog>`. Updates: `[p]repo update`, `[p]cog update`, per-cog **pin/unpin** (version locking), install/update to a specific git **commit** (`[p]cog installversion`, `[p]cog updatetoversion`). Cog management commands are **locked to the bot owner**. Local development uses `[p]addpath`.
- **Dependency execution:** `requirements` in `info.json` are **passed to pip at cog install time** (the publish guide says so explicitly). So installing a cog can execute arbitrary Python at install time and pull arbitrary PyPI/git dependencies.
- **Runtime model — no sandbox:** cogs are ordinary Python classes imported into the bot process ("Subclassing to make changes to Red's cogs/extensions…", "Overriding Permissions specifically is dangerous" are the docs' only warnings). A cog sees the whole data directory, the config subsystem and the bot token, and can `import` anything. There is no capability model, no permission manifest, no isolation. The trust model is **social**: an "Approved Cog Creator" application reviewed by QA on `cogboard.discord.red` (requirements include "No cog contains malicious code", "No cog allows for escalation of permissions", "respect the role hierarchy"; repos that break and aren't fixed in 1 month get **delisted**). Repos outside the approved set are listed as *unapproved* with a blunt banner: "Unapproved repositories are provided by the community and have not yet been inspected."
- **RPC (the integration hook for dashboards/other languages):** with `--rpc`, Red opens a **localhost WebSocket JSON-RPC server on 127.0.0.1:6133** (deliberately not configurable — "broad access to this server gives anyone complete control over your bot"). Cogs register handlers; clients (dashboards, bots) can call methods and subscribe to event topics. This exists precisely because third parties wanted to control Red externally — and it is marked *provisional* and can be changed/removed.
- **Permissions for users:** Red ships a core Permissions cog giving per-command, per-channel, per-role rule management, plus bot-owner concepts; the README advertises "Customisable command permissions".

### 1.2 Third-party dashboards for Red

- **Red-Dashboard (NeuroAssassin; later moved into the Cog-Creators org):** archived **Mar 2, 2025** with an "EoL Announcement" commit; the README now says: *"This project is discontinued, is no longer supported, and is known to be completely non-functional. If you are searching for a dashboard, please search the Index for one in active development."* 77 stars, 43 forks, 138 commits, AGPL-3.0. Its architecture was a separate Flask app talking to Red over RPC, with Discord OAuth login. The EoL reason isn't documented publicly, but the pattern (single-maintainer project, moved to the core org, then terminated) is the classic OSS handoff failure.
- **Auttaja** (Python/discord.py + custom dashboard): see §2 — the owner's 2021 post-mortem says the dashboard "sucks… it hardly works on mobile… issues loading and saving configuration data", and the project is now offline (site shows "Coming soon"; listed offline Aug 2026).
- **What exists today:** the de-facto Red dashboard is a **cog**: `AAA3A-cogs/dashboard` — an approved repo whose 79 cogs were *all* updated in the last 12 months — described as "Interact with your bot through a web Dashboard! Thank you very much to Neuro for the initial work!", with pip requirements `git+AAA3A_utils`, `fernet`, `markdown2`, `wtforms`, `werkzeug`, `markupsafe`, `itsdangerous`. I.e., **the dashboard became a Flask/Werkzeug app installed as a plugin, because core Red never exposed a first-class web/API surface**. NeuroAssassin's own `Toxic-Cogs` still ships a `dashboard` cog (a relic of the old Red-Dashboard protocol). Nobody has rebuilt a modern, maintained, org-backed dashboard for Red — that door is wide open.

## 2. Other open-source bots worth learning from

**YAGPDB (`botlabs-gg/yagpdb`) — the best "bot + first-party control panel" precedent.** Go, MIT, 1,449 stars, **very active**: v2.87.1 published 2026-09-27. It is modular ("for most things plugins exist"), ships Docker/docker-compose for self-hosting, and the repo contains the `web` control-panel code powering `yagpdb.xyz/manage` — i.e., *the dashboard lives with the bot*, and the same binary/panel serves both the hosted service and self-hosters. This is the closest existing model to what we intend to build (minus TypeScript and minus a plugin SDK for third parties).

**sushii — the cautionary tale of serial rewrites.** `sushiibot` org has 25 public repos. History: `sushii-bot` (Rust, serenity-rs, PostgreSQL/diesel) marked "no longer active or maintained"; `sushii-2` (Rust rewrite, AGPL-3.0, 22 stars, last push Sep 2025, homepage sushii.xyz); and now a **third generation** in TypeScript (`sushiibot/sushii`, topics `discordjs` + `bun`, AGPL-3.0, pushed 2026-09-23, homepage sushii.bot) with satellites: `sushii-modmail` (TS, active Sep 2026), `sushii-agent` (TS, updated Oct 6 2026), `sushii-analytics`, `sushii-workflows`, and an older Next.js+PostGraphile web app (last pushed Jan 2024). Three stacks in ~4 years for one mid-size community-management bot; the web app always lagged the bot.

**Loritta — the OSS-reciprocity failure.** A 1M+-guild Kotlin bot (built on the org's JDA fork `DeviousJDA`). On **May 23, 2026** the main repo was **archived and Loritta went closed source**: the repo notice says *"We've decided to change Loritta to be closed source, sorry! The reason why we did this is because Loritta was not getting anything 'back' from her being open source (users contributing to the project…)"*, expanded in the owner's blog post "Open Source para Closed Source" (2026-05-23). Lesson: OSS + hosted service + zero monetization corrodes when external contribution never materializes.

**Auttaja — the classic decline post-mortem.** Python + discord.py + an in-repo dashboard (added 2018). The owner's 2021 Medium post is the most candid OSS-bot autopsy available: dashboard unmaintainability ("way too many new features hacked into the codebase… miserable maintainability"), "our development team has been unmotivated to work on the bot" for ~2 years, hosted costs never broke even, and an abandoned Go rewrite meta-repo (`Auttaja-OpenSource/Core`, last push Jan 2019). The bot is offline; the domain is a placeholder.

**Framework-adjacent ecosystems (learn for the plugin market, §4):** **NoneBot2** (Python, 7,735 stars, MIT, active Oct 2026) has an official plugin registry listing **942 plugins**; **Koishi** (TypeScript, 6,245 stars) advertises in its README an "online plugin marketplace" installable from its web console "even without any programming knowledge". Both prove that "install plugins from a curated marketplace, from the UI" is an expectation users already have.

## 3. Framework health (Oct 2026)

**TypeScript/JS**
- **discord.js** — 26,818 stars, Apache-2.0, the reference library. Stable: **14.27.0 (2026-07-15)**. **v15.0.0 is unreleased**: the milestone shows **94% complete** (checked 2026-10-07), nightly `15.0.0-dev.*` builds are on npm, and a "Updating to v15" guide already exists on discordjs.guide (notable: WebSocket behaviour fully integrated). Plan for a 14.x → 15 migration; don't build on dev builds.
- **Sapphire (`sapphiredev/framework`)** — 756 stars, MIT, **v5.5.1 (2026-08-22)**, commits this month. The mature "batteries-included" layer on discord.js (module system, stores, preconditions). Small maintainer team, narrow scope.
- **seyfert** — 321 stars, MIT, npm **v5.1.0**, repo pushed today (2026-10-07). Small, opinionated, npm-only release cadence. Viable but thin ecosystem.
- **DiscordX** — 737 stars, Apache-2.0, npm 11.13.3; **last GitHub release `discordx@11.12.0` was 2024-06-29**; last push 2026-07-29. Slowing but not dead.

**Python**
- **discord.py** — 16,197 stars, MIT, active (pushed 2026-09-07). Latest **2.7.1 (2026-03-03)**; v2.7.0 added DAVE (voice E2EE) support, new modal components (checkbox/radio groups), `@time` timestamp converters; v2.7.0/2.7.1 already fix issues "under Python 3.14". Healthy, but a one-maintainer (Rapptz) project in practice.
- **Pycord** — 2,958 stars, MIT, **2.8.1 (2026-07-25)**; 2.8.0 added Python 3.14 support; a separate **Pycord v3** ("modern, extensible architecture", pre-release, `pip install git+…/pycord-v3`) is in development. Pushing the "next generation" narrative.
- **Nextcord** — 1,263 stars, MIT, **3.2.0 (2026-05-21)**, requires **Python ≥3.12**; still maintained after its post-2021 fork drama, but smallest of the three.

**Rust**
- **serenity** — 5,625 stars, ISC, latest **0.12.5 (2025-12-20)**, active commits (Oct 3, 2026). Mature, but 0.x still.
- **twilight** — 879 stars, ISC, **0.17.1 (2025-12-13)**, active (pushed Oct 7, 2026). Technically excellent, niche.

**What the biggest bots run:** Red = Python/discord.py; YAGPDB = **Go**; Loritta = **Kotlin** on a JDA fork; sushii = Rust (serenity → twilight-family) now **TypeScript + Bun + discord.js**; the commercial leaders (MEE6, Dyno, Carl-bot, Wick) are **closed source with no first-party stack documentation** — MEE6's public profile is a tiny engineering team (a CTO profile claims ~4 engineers for 21M+ communities), funded by paywalled premium features. Nothing in the top tier is built on a sandboxed plugin ecosystem; the two OSS leaders (Red, YAGPDB) both accept in-process plugins/plugins-as-code with review-based trust.

## 4. Plugin-system & sandboxing precedents (and marketplaces)

**Sandboxing techniques, state of the art:**
- **`node:vm` / vm2 — do not use for adversarial code.** vm2 (4,101 stars) was abandoned after 2023 escapes, then **revived by its original author**: npm 3.10.0 (2025-10-24), 3.11.0 (2026-05-01), 3.12.0/3.12.2 (Sep 2026). Escapes continue anyway: "VM2 Has a WASM Sandbox Escape" **CVE-2026-26956** (published 2026-05-01) and a JSPI-backed Promise bypass (GHSA-6j2x-vhqr-qr7q, May 2026). Its README now carries a security disclaimer recommending process/hardware-level isolation instead. Node's own permission docs are explicit: *"This feature does not protect against malicious code. According to the Node.js Security Policy, Node.js trusts any code it is asked to run."*
- **isolated-vm** — 2,934 stars, ISC, **v6.0.2 (2025-10-16)**, repo still receiving commits (pushed 2026-10-07), 97 open issues; README's user list: Screeps, Fly, Algolia, Tripadvisor. Best in-process JS isolation (separate V8 isolates, explicit `Reference`/`ExternalCopy` data passing), but vm2's README characterizes it as "in maintenance mode" and it requires manual V8/Node upgrades. Fine for *limiting* pure-logic plugins; not a full trust boundary for a bot that holds a token.
- **Process/worker isolation** — `worker_threads`/`child_process` with a serialized IPC API is Node's honest boundary; heavier, but the recommended pattern once code is untrusted.
- **Deno subprocess workers** — deny-by-default flags confirmed on docs.deno.com: `--allow-read/-write/-net/-env/-run/-ffi/-import/--allow-all`. Running each plugin as a Deno child with a narrow allow-list (no `--allow-run`, no `--allow-ffi`, network restricted to Discord API hosts) gives a real capability sandbox. Cost: a second runtime in the deployment (Docker image, not a problem for us) and IPC serialization.
- **WASM** — `quickjs-emscripten` runs JS in a WASM QuickJS VM (used by TLSNotary's extension for "capability-based" plugins); **Extism** is a cross-language WASM plugin framework ("off-the-shelf plug-in system") with host functions exposed deliberately. Strong isolation + cheap to embed; weakest ergonomics for authors who expect full Node APIs.

**Marketplace precedents:**
- **Red-Index** is the most directly applicable. Mechanically: a YAML list in `Cog-Creators/Red-Index` (today: **58 approved, 49 unapproved repos**), a **GitHub Actions job every 15 minutes** that clones every repo and compiles a public JSON (`index/1-min.json` — today **105 repos / 1,306 cogs**), consumed by `index.discord.red` and an in-bot Index cog (install repos/cogs from inside Discord). Two tiers: *approved* (QA-reviewed Cog Creator applications) and *unapproved* (PR self-submission, shipped with the "use at your own risk / not inspected" banner). Weaknesses: review is a human bottleneck; no signatures/integrity; versioning is "track a git commit"; no automated static analysis; abandonware only delisted *after* visibly breaking.
- **Red's in-bot flow proves demand:** users install third-party code with a two-line chat command. That UX is worth copying — with better safety rails.
- **Koishi / NoneBot2** (above): web-console marketplaces installing npm/PyPI packages; NoneBot2's registry has 942 plugins.
- **HACS (Home Assistant)** — a mature curated-store precedent: contributions are PR-gated with a manifest (`hacs.json`) and default-store inclusion is reviewed by maintainers (`hacs.xyz/docs/publish/*`).
- **Extism** — distribution-as-artifact (WASM modules) rather than distribution-as-source, enabling signing and version pinning as first-class.

## Lessons to steal

1. **Install-from-chat is the killer UX.** `[p]repo add` + `[p]cog install` converted a chat command into a package manager; replicate it as slash commands *and* in-dashboard one-click installs, with a compatibility table per module (Red's `min_bot_version`/`min_python_version` metadata is a good primitive).
2. **An auto-maintained public index is cheap and high-leverage.** Red-Index = one YAML + a 15-minute GitHub Action + public JSON. That's a marketplace backend for ~zero ops cost; our equivalent should also carry signature status, last-updated, and compat ranges.
3. **Two-tier trust (reviewed vs self-published) works.** Approved/QA-reviewed tier with real delisting rules + an "unapproved, uninspected" tier is a pragmatic compromise; add automated gates (manifest lint, static scan, permission diff) that Red lacks.
4. **Dashboards must be core, not a bolt-on.** Red's only living dashboard is a Flask app installed as a cog; YAGPDB's panel ships in-repo and serves both hosted and self-hosted. Our monorepo (apps/web + module page registry) is the right call; keep "bot ↔ web" contracts versioned from day one.
5. **Ship a control-plane API (Red RPC) — but safely.** Red's localhost-only, token-less WebSocket is why dashboards were fragile and why RPC "may be removed". Ours should be authenticated, versioned, and documented as a stable module contract.
6. **Version guarantees + migration notes.** Red's "Read before updating" sections and guarantees page are why users trust updates; replicate per-release.
7. **Docs and OAuth-scoped, per-guild dashboards.** Discord-OAuth login with per-guild permission scoping (Red-Dashboard's best idea) is table stakes.
8. **Free-forever is a real differentiator** — the loudest r/discordapp complaints about MEE6/Dyno are paywalls; Red's and YAGPDB's communities stay partly *because* everything is free.
9. **Container-first distribution.** Red maintains ~20 OS install guides and still fights Python/Java versions; YAGPDB's `docker-compose` path is one page. Compose-first, OS-agnostic.
10. **Ride the JS ecosystem's health.** discord.js/Sapphire/Pycord are all moving (discord.js v15 at 94% of milestone; discord.py shipping DAVE support) — a TS stack inherits updates that Red literally cannot take (Python <3.12).

## Mistakes to avoid

1. **Don't let the runtime age.** Red's `>=3.8.1,<3.12` ceiling is 3+ years behind; pin *minimums*, never maximums, and add runtime-matrix CI.
2. **Don't treat "review" as a security boundary.** Red cogs = arbitrary in-process Python with pip installs; the QA process is a human check, and the platform's own advisories show how much damage one core bug can do. If we run third-party code, either (a) sandbox with real boundaries (Deno subprocess / WASM / separate process), or (b) state the trust model loudly and add scanning + provenance.
3. **Don't let a flagship dashboard be a one-person side project.** Red-Dashboard's death ("completely non-functional") permanently damaged the platform's appeal; Auttaja's dashboard rot did the same. Also: don't strand the dashboard at the CDN/cache level — keep it in-monorepo.
4. **Don't rewrite the whole bot twice.** sushii went Rust → Rust → TS/Bun in ~4 years; each rewrite reset its ecosystem. Pick the stack once (TS/discord.js), and grow the module API behind stable boundaries.
5. **Don't ship a plugin API whose plugins need root.** AAA3A's dashboard cog pip-installs Werkzeug/fernet etc. into the bot venv; each such dependency is an unpinned supply-chain risk. Constrain module dependencies (allowlists, lockfiles, vendored SDK).
6. **Don't skip version pinning/rollback.** Red only recently got per-cog pinning; modules must be installable at exact versions with one-click rollback in the dashboard.
7. **Don't ignore the audio trap.** Red's Java/Lavalink dance and its issue tracker are a warning: if we do music, do it with `@discordjs/voice`-style libraries and optional external nodes, and make failures degrade gracefully.
8. **Don't assume open source automatically builds a contributor base.** Loritta's 2026 closure and Auttaja's burnout both trace to "OSS in name, single-team in practice, zero reciprocity". Budget community management (CONTRIBUTING, good-first-issues, maintainer roles) or don't promise it.
9. **Don't leave gateway/API migrations to chance.** Red's users literally asked whether the bot survives Discord's slash-command reality. Track Discord API deprecations with owned milestones.
10. **Don't choose a license that contradicts the business intent.** Red is GPL-3.0 — anyone may commercially host/modify it. "Clone with credit, no monetized clones" is *not* achievable with GPL/AGPL; it needs a source-available license (e.g., PolyForm-style noncommercial) and/or trademark+hosted-service moats. Decide before publishing, because Loritta's U-turn shows how painful re-licensing is after the fact.

## Implications for our build

- **Module contract first.** Mirror Red's `info.json` primitives (id, version, author, `requirements`, `min_bot_version`/`max_bot_version`, `min_python`→`min_runtime`, end-user-data statement, tags) **plus** what Red lacks: a declared capability list (which Discord events, intents, DB tables, HTTP endpoints, dashboard pages it wants), a dashboard-page manifest, and semver.
- **Three-tier execution plan:** (1) built-in modules = first-class trusted code in `apps/bot`; (2) community modules = loaded through the SDK, with declared capabilities enforced at the API layer + automated static checks; (3) untrusted/experimental modules = optional Deno-subprocess or WASM worker mode (opt-in), because Node's own docs say in-process isolation "does not protect against malicious code".
- **Marketplace v1 = Red-Index + HACS mechanics, minus the weaknesses:** a public index service (JSON) refreshed by CI from a reviewed `modules.yaml`, in-bot slash install commands, one-click dashboard install, per-module compat ranges checked at install time, signature/checksum verification, automated manifest+lint gates, and an "unreviewed" badge for self-published modules.
- **Dashboard as a product surface:** Next.js app + bot RPC/HTTP control plane (authenticated, versioned), Discord OAuth with per-guild scoping, module pages registered via `packages/core` so a module's UI ships with the module — this is exactly what Red never had and what AAA3A had to hack into a cog.
- **Ops posture:** Docker Compose as the primary self-host path (YAGPDB model), Postgres+Redis in-compose profile, one-command upgrade + automatic migrations; avoid external runtimes (Java) unless optional and isolated.
- **Governance & funding:** plan maintainer roles and a public roadmap from day one (Red's bus factor shows what happens otherwise); fund via donations/sponsorships (Red's own README asks for Patreon support) rather than paywalled features, since "everything free" is the wedge — and note the hosted-cloud instance must be genuinely optional, not artificially better than self-host.
